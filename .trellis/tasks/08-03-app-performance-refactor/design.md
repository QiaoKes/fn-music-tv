# Technical Design

## Architecture And Boundaries

重构以“状态变化频率”和“职责所有权”为两个切分轴：

- UI 层只消费页面所需的稳定状态切片，并通过动作接口发出意图。
- 播放层区分高频进度、低频播放元数据和结构性队列状态，避免一个状态对象驱动全部界面。
- 业务编排层负责会话退出、播放停止、缓存切换和鉴权恢复等跨模块流程。
- 数据层负责网络、缓存和持久化实现，通过窄接口向上暴露能力。
- 路由状态由返回栈所有，进入栈时建立，永久出栈时回收。

## State And Data Flow

1. 播放器事件先分类为进度事件、元数据事件和结构事件。
2. 进度事件只更新播放器页面使用的进度流；结构事件才重新投影队列。
3. UI 根节点只观察会话状态；具体页面在最小作用域内观察所需播放切片。
4. 页面动作调用显式 action/controller 契约，跨层副作用由业务编排器串联。
5. 持久化快照先在后台串行编码，再由现有 revision 机制提交，旧请求不得覆盖新请求。

## Lifecycle And Cache Policies

- 返回栈内的页面状态继续保留；页面永久出栈后同步清理 retained state 和 saveable state。
- 图片缓存维护增量大小账本，并仅在越过阈值时安排剪枝；仍保留启动/异常恢复时的全量校准。
- 数据库预算检查采用低频或越界触发，轻量统计与昂贵 checkpoint/vacuum 分开执行。
- 安全存储在 IO dispatcher 读取，`SessionState.Loading` 作为初始化期间的既有可见状态。

## Compatibility

- API 23 兼容修复使用显式条目迭代，保持 header 覆盖顺序和内容不变。
- 不修改数据库 schema、序列化字段、媒体 ID、队列上限、路由 storage key 或用户可见错误。
- 拆分文件时保持现有 internal/public API，必要时先建立兼容适配层再移动实现。

## Trade-offs

- 使用多个窄状态流会增加少量模型数量，但能隔离 4 Hz 更新并明确依赖方向。
- 增量缓存账本需要异常校准路径；以保留全量扫描作为低频恢复机制换取写入热路径性能。
- 架构解耦在性能热点稳定后执行，避免同时改变状态传播与模块依赖导致回归难定位。

## Rollback

- 六个子任务独立实现和验证，任何阶段失败时只回退当前阶段。
- 播放、持久化、缓存和路由变更均先补充契约测试；不采用不可逆的数据迁移。
- 性能优化若无法证明行为等价，保留原实现并记录为 deferred item。

# App 等量重构与性能优化

## Goal

在不改变业务逻辑、UI 布局、焦点行为和控制逻辑的前提下，分阶段降低主线程工作量、无效重组、长期状态占用和模块耦合，并建立可重复验证的性能与质量基线。

## Confirmed Facts

- App 最低支持 Android API 23，当前 `core:data` lint 因两个 Java `Map.forEach` 调用要求 API 24 而失败。
- 播放进度每 250 ms 更新一次，根 Composable 收集完整 `PlaybackUiState` 并向已登录界面下传。
- 播放状态投影会重建最多 250 项的队列视图；播放快照编码位于调用方线程。
- 动态路由保留状态使用无上限 Map 和 `SaveableStateHolder`，退出详情页时没有显式释放。
- 图片缓存每次新增写入后全盘扫描和排序；本地数据库预算检查包含多次聚合查询与空间回收。
- UI 直接依赖 `AppContainer`，并承担退出登录、缓存清理、播放协调和错误字符串识别等跨层编排。
- `AuthenticatedApp.kt` 和 `PlaybackController.kt` 分别约 4416 行和 1353 行，且存在已无调用的旧 UI 代码。

## Requirements

- R1：保持登录、首页、我的、详情页、焦点移动、返回栈、播放队列、播放模式、漫游播放、恢复播放和缓存语义不变。
- R2：保持现有 UI 布局、文案、控件位置、焦点图和用户可见控制响应不变；仅调整内部状态边界和代码组织。
- R3：按以下顺序交付并独立验证子任务：
  1. Android 23 兼容性与质量基线
  2. 播放状态边界与主线程性能
  3. 路由状态生命周期治理
  4. 缓存与启动性能优化
  5. UI、业务编排与数据层解耦
  6. 源码清理与性能回归验证
- R4：非播放器页面不得因 250 ms 播放进度变化而整体重组；队列投影不得因纯进度事件重复构建。
- R5：快照序列化、缓存目录扫描、数据库回收和安全存储读取不得造成可避免的主线程阻塞。
- R6：动态页面状态必须有与路由生命周期一致的回收策略，且不得破坏返回页状态恢复。
- R7：UI 只能依赖明确的状态与动作契约；跨仓库/缓存/播放协调由单一业务编排边界负责。
- R8：不改变服务端 API、数据库 schema、持久化兼容格式、minSdk、播放协议或现有错误语义。
- R9：每个子任务都应保持可独立回退，并在进入下一个子任务前通过相应单元测试、lint 和结构检查。

## Acceptance Criteria

- [x] 六个子任务按 R3 顺序完成、检查并归档。
- [x] `./gradlew test lint --continue` 通过，API 23 lint 错误归零。
- [x] 登录、浏览、详情、返回、焦点、播放控制、队列、模式、漫游和恢复行为与重构前一致。
- [x] 非播放器页面不再订阅 250 ms 进度状态；纯进度刷新不重建完整队列。
- [x] 播放快照 JSON 编码不在主线程执行，写入顺序与 revision 语义保持不变。
- [x] 已移出返回栈的动态页面状态可回收，返回栈内页面仍可恢复。
- [x] 图片缓存新增写入不再无条件触发全目录扫描排序；数据库预算治理避免每次写入执行完整重回收流程。
- [x] 会话安全存储读取不阻塞 Application 初始化主线程。
- [x] UI 不再通过 `AppContainer` 直接编排退出登录、缓存和播放清理；错误处理不依赖字符串包含判断。
- [x] 完成设备可用时的基准/Profile 验证；若当前无设备，明确记录未执行项和可复现命令。

## Out of Scope

- UI 重设计、动画变化、文案调整和导航体验改版。
- 新业务功能、服务端接口或数据库 schema 变更。
- 音频文件缓存策略重做、依赖大版本升级和构建系统迁移。
- 为追求抽象而引入新的框架或跨模块公共层。

## Technical Notes

- 优先采用现有 Kotlin Flow、Compose 生命周期、协程和模块边界，不新增状态管理框架。
- 每个阶段先固定行为测试，再做等量替换；涉及持久化和播放顺序的改动必须保留 revision、namespace 和恢复契约。

# 设置页版本信息、应用内更新与发布后台

## Goal

在保持回声台现有 Android TV 深色视觉、遥控器焦点和触屏操作方式的前提下，为用户提供清晰的版本与开源项目信息、可靠但不打扰播放的更新检查，以及简单的 App 内下载安装流程；同时提供一个只服务回声台的 Cloudflare 可视化发布后台，让开发者可以从 GitHub Release 选择版本并安全发布到 R2。

## Background

- 当前设置页为纵向滚动的 Compose for TV 页面，已有播放界面、在线歌词匹配、缓存上限和清缓存设置。
- 应用版本由根目录 `version.properties` 管理，并在 `app/build.gradle.kts` 中映射到 Android `versionName` / `versionCode`。
- 当前 GitHub 发布流程只产出供侧载安装的 universal APK 及其 SHA256；本功能仅面向该 APK，不涉及应用商店渠道。
- 用户已确认纵向设置页视觉稿：现有设置区域在上，“关于”区域在下，不显示“确认键手动检查”。
- 用户已确认更新弹窗视觉稿：显示当前/最新版本、更新摘要，以及“立即更新”“稍后提醒”“忽略 <版本>”三个操作。
- 中国大陆可用性是选择更新基础设施的主要原因。应用内更新只使用 Cloudflare R2 自定义域名，不回退到 GitHub、`ghfast.top`、浏览器或其他更新源；该链路在大陆属于尽力可用，不承诺 Cloudflare 中国网络级别的可用性。

## Requirements

### R1 设置页与关于信息

- 设置页继续使用纵向、可滚动布局，不改成左右两栏页面。
- 现有播放界面、在线歌词匹配、缓存上限和清缓存功能保持行为不变。
- 使用现有 `FnColors`、圆角、间距和珊瑚色焦点样式；所有新增操作同时支持遥控器与触屏。
- 页面在 1920×1080 横屏安全区域内可浏览；较小横屏视口可通过现有纵向滚动访问全部内容。
- 在现有设置项下方新增“关于”区域，显示：
  - 应用名称“回声台”；
  - 运行包的实际 `versionName（versionCode）`；
  - 作者 `Tag mig hånden`；
  - GitHub 仓库地址 `github.com/QiaoKes/fn-music-tv`。
- 版本信息必须来自构建产物，不得在 UI 中重复硬编码。
- “关于”区域提供可聚焦、可触摸的“检查更新”入口，且不显示“确认键手动检查”。

### R2 更新检查时机与结果

- 每次应用进程启动后异步检查一次更新，不阻塞首页加载。
- 进程持续存活时，以内存状态安排后续检查；任意一次自动或手动检查成功后，重新开始计算 12 小时。
- 自动检查失败后 30 分钟重试；自动失败保持静默，不打断用户。
- 进程退出后不保留检查时间；下次启动重新执行启动检查。
- 设置页手动检查不设频率限制。手动检查失败时明确提示可重试；没有新版本时明确提示已是最新版本。
- 自动检查发现更新时，首页稳定后再显示弹窗；若用户正在全屏播放，则将提示保留在内存中，等用户回到首页或设置页后再显示。
- 手动检查发现更新时立即显示更新弹窗，不受自动提示延迟规则影响。

### R3 版本判断与忽略规则

- Android `versionCode` 是判断版本新旧和忽略记录的唯一顺序依据；`versionName` 只用于展示。
- 自动检查时，只有线上 `versionCode` 大于当前安装版本才视为有更新。
- 用户选择“忽略此版本”后，按该版本的 `versionCode` 保存设备全局忽略记录；该记录不跟随 NAS 账号。
- 自动检查发现的最新版本正好已被忽略时，不显示更新弹窗。
- 发布更高 `versionCode` 后必须重新提示，不受旧忽略记录影响。
- 设置页手动检查时，即使线上版本已经被忽略，也必须显示更新弹窗并标注“此版本已忽略”，用户仍可立即更新。
- 安装新版本成功后，在下次启动时清理所有低于当前 `versionCode` 的忽略记录。
- 不提供强制更新：所有更新都允许稍后提醒或忽略，更新服务失败不得阻止用户继续使用应用。

### R4 R2 更新来源与发布一致性

- App 只从构建时固定的 R2 HTTPS 自定义域名读取更新清单和下载 APK；普通用户不能在 App 内修改更新地址。
- sideload 正式构建必须配置更新清单地址；缺少地址时构建失败。调试构建可以关闭更新检查或使用测试地址；store 渠道不启用自更新。
- APK 使用包含 `versionCode` 的不可变版本化路径，已经发布的 APK 不覆盖、不自动删除。
- 每次发布必须先完成 APK 上传和校验，最后才更新对外的 `update.json`，避免清单先于安装包生效。
- `update.json` 不使用独立数字签名，也不引入额外更新签名密钥。
- `update.json` 至少提供包名、版本名、版本号、更新标题与说明、APK HTTPS 地址、文件大小、SHA256 和发布时间等检查更新所需信息。
- App 不使用 GitHub Release、GitHub API、`ghfast.top` 或其他代理作为检查或下载的备用源。

### R5 更新弹窗、下载与系统安装

- 新版本弹窗显示应用名称、当前版本、最新版本和更新摘要，并提供“立即更新”“稍后提醒”“忽略 <最新版本>”三个独立操作。
- 默认焦点落在“立即更新”；遥控器方向键的焦点顺序明确，三个操作均支持触屏且单次操作只触发一次。
- 点击“立即更新”后，原弹窗切换为下载进度，只显示百分比、已下载大小和“取消”。
- 下载仅在 App 前台执行，不使用通知栏、后台服务或断点续传：
  - 用户按返回、点击取消、退出 App 或在下载期间将 App 切入后台时，立即取消下载并删除未完成文件；
  - 下次更新必须重新下载；
  - 下载完成并校验通过后，为安装授权或系统安装而离开 App 不视为取消。
- 下载完成后必须校验 APK 的 SHA256、包名、`versionCode` 和应用签名；任一项不匹配时禁止进入安装流程并清理无效文件。
- APK 的包名必须是 `com.fnmusic.tv`，`versionCode` 必须高于当前安装版本，APK 签名必须与当前已安装应用一致；Android 系统安装阶段仍需再次完成平台校验。
- 若当前 App 尚无“安装未知应用”权限，在 APK 下载并校验完成后先解释原因，再引导用户打开该 App 的系统授权页；用户返回且授权成功后自动继续安装。
- 最终安装必须由 Android 系统显示确认页面，普通用户明确确认后才安装；不做静默安装。
- 用户取消授权或取消系统安装后，给出可理解的结果并清理临时 APK；下次需要重新下载。

### R6 GitHub Release 构建元数据

- GitHub Release 构建流程除 universal APK 和 `.sha256` 外，还必须生成并上传 `release-metadata.json`。
- `release-metadata.json` 至少包含：
  - `packageName`；
  - `versionName`；
  - `versionCode`；
  - APK 文件名、大小和 SHA256；
  - APK 签名证书指纹；
  - 构建时间和 Git commit。
- 发布后台必须以该元数据为版本信息来源，并与实际 APK 和 GitHub Release 资源相互校验；信息缺失或不一致时禁止发布。
- 旧 Release 若缺少该元数据，可以在后台查看，但不能直接发布到 R2。

### R7 单应用可视化发布后台

- 在仓库 `tool/` 目录下提供一个只服务回声台的发布工具，可直接部署为 Cloudflare Worker，并同时提供中文可视化管理 UI 和发布接口。
- 第一版只管理一个应用和一个 R2 更新源，不支持多应用、多租户或复杂角色权限。
- 后台配置一次 GitHub 仓库地址后，通过 GitHub Releases API 展示可选择的 Release、发布时间、更新说明和资产信息。
- 默认只显示正式 Release；预发布版本默认隐藏，用户可以显式开启显示，但发布预发布版本前必须出现明显的二次警告；草稿 Release 永远不得发布。
- 第一版只支持从已配置的 GitHub Release 选择 APK，不支持本地上传，也不自动猜测或发布 GitHub 的“最新版本”。
- 选择 Release 后，后台自动选取符合配置规则的 APK，下载并校验 `release-metadata.json`、文件大小和 SHA256，再上传到 R2 的版本化路径。
- 更新标题与说明默认取 GitHub Release 内容，发布前允许编辑；编辑只影响 App 更新弹窗，不反向修改 GitHub Release。
- 正式发布前必须显示最终预览和二次确认，至少明确展示版本、APK、SHA256、更新说明和 R2 地址；只有再次确认后才更新 `update.json`。
- 后台记录实际发布内容和历史版本。所有已发布 APK 永久保留，不提供自动清理或删除功能。
- 后台提供“撤回当前版本”：将 `update.json` 恢复为上一个已发布版本并使新清单尽快生效，但不删除 APK。
- 撤回只阻止尚未升级的设备继续收到问题版本；已安装问题版本的设备不自动降级，必须等待更高 `versionCode` 的修复版。
- 除首次建立发布基线或执行历史撤回外，新的正式发布必须使用高于历史最高已发布值的 `versionCode`，禁止将较低或相同版本伪装成新更新。

### R8 发布后台部署与安全边界

- 后台通过 Cloudflare Access 保护，只允许配置的管理邮箱访问页面和发布接口；接受首次开通 Zero Trust 免费套餐时可能要求绑定付款方式。
- 发布工具提供中文初始化/部署流程，通过 Cloudflare 浏览器授权完成登录和部署，不要求用户在管理 UI 中输入或保存 Cloudflare API Token。
- Worker 运行时通过 R2 Binding 读写存储桶，不在代码、网页或普通配置中暴露 R2 凭据。
- GitHub 仓库为公开仓库，但生产 Worker 必须使用只限 `QiaoKes/fn-music-tv`、仅 `Contents: Read-only` 的 Fine-grained PAT，避免 Cloudflare 共享出口耗尽 GitHub 匿名 IP 额度；Token 只保存为 Worker Secret，不进入网页配置、R2 或代码。第一版仍不支持私有仓库。
- 后台可配置 GitHub 仓库、APK 资产匹配规则、R2 公共下载域名、对象路径、应用包名和列表展示数量等非敏感信息。
- R2 Bucket Binding、Cloudflare Access 策略和其他权限配置属于部署配置，不允许通过网页后台随意切换。

## Acceptance Criteria

- [ ] AC1：设置页保持纵向滚动，现有设置功能行为不变；新增“关于”和更新操作均可通过遥控器和触屏完成。
- [ ] AC2：“关于”区域展示运行包实际 `VERSION_NAME（VERSION_CODE）`、作者 `Tag mig hånden` 和正确 GitHub 仓库地址，代码中没有重复硬编码版本号。
- [ ] AC3：“检查更新”入口不存在“确认键手动检查”文案；手动检查不受频率和忽略记录限制，并正确展示最新版、已忽略、失败及发现更新等结果。
- [ ] AC4：每次进程启动异步检查；成功检查后 12 小时再检查，失败后 30 分钟重试；关闭进程后计时不持久化，自动失败保持静默。
- [ ] AC5：自动更新弹窗不会覆盖全屏播放；回到首页或设置页后能够补充显示，手动检查则立即显示。
- [ ] AC6：自动检查不会提示已忽略的相同 `versionCode`，更高版本会重新提示；忽略记录为设备全局状态，安装新版后旧记录得到清理。
- [ ] AC7：App 的更新请求和 APK 下载只访问构建时固定的 R2 HTTPS 域名，不访问 GitHub、代理或其他备用更新源；正式构建缺少更新地址时失败。
- [ ] AC8：更新弹窗和下载进度符合已确认视觉及焦点规则；取消、返回或下载期间离开 App 会停止下载并删除未完成文件，不产生后台下载或续传。
- [ ] AC9：只有 SHA256、包名、更高 `versionCode` 和 APK 签名全部校验通过后才进入系统安装；未授权时先引导授权，最终始终由系统要求用户确认安装。
- [ ] AC10：CI 为每个新 GitHub Release 生成完整 `release-metadata.json`；发布后台拒绝元数据缺失、内容不一致或 APK 资产不唯一的版本。
- [ ] AC11：`tool/` 下的发布后台可通过浏览器授权部署到 Cloudflare Worker，使用 R2 Binding，并由 Cloudflare Access 限制管理邮箱；网页中不存在 CF Token 或 R2 密钥输入项。
- [ ] AC12：后台能够配置 GitHub 仓库、列出并选择 Release；正式版默认可见，预发布版需显式开启并二次警告，草稿不可发布，本地 APK 不可上传。
- [ ] AC13：选择 Release 后可以自动下载、校验、上传版本化 APK，带入并编辑更新说明，预览最终内容，并通过二次确认最后发布 `update.json`。
- [ ] AC14：新发布不会覆盖或删除历史 APK；“撤回当前版本”可恢复上一份清单，但不会让已升级设备降级；后续修复版必须使用更高 `versionCode`。
- [ ] AC15：所有更新均可稍后提醒或忽略；更新检查、下载或安装失败不阻止用户继续使用回声台。
- [ ] AC16：相关单元测试、Compose UI 测试、网络与持久化测试、发布后台测试、App 编译、lint 和发布工具构建均通过。

## Out of Scope

- Google Play、其他应用商店、商店内更新 SDK，以及 `store` 渠道的自更新。
- GitHub、`ghfast.top` 或其他代理作为 App 端更新检查与下载备用源。
- 强制更新、灰度发布、多更新渠道和按账号下发更新。
- 后台下载、通知栏下载、系统 DownloadManager、断点续传和进程死亡恢复。
- 静默安装、设备所有者安装和绕过 Android 系统确认。
- 独立的 `update.json` 数字签名、更新签名私钥及其轮换/备份体系。
- 发布后台的多应用、多租户、复杂角色、私有 GitHub 仓库和本地 APK 上传。
- 历史 APK 自动清理或删除，以及已安装问题版本的自动降级。

## Deferred Inputs and Risks

- 生产部署已确定：R2 Bucket 为 `fn-music-tv-updates`，公共下载域名为 `https://<R2_PUBLIC_DOMAIN>`，发布后台为 `https://<PUBLISHER_DOMAIN>`，Cloudflare Access 仅允许 `<ADMIN_EMAIL>`，正式 `UPDATE_MANIFEST_URL` 为 `https://<R2_PUBLIC_DOMAIN>/update.json`。
- GitHub Actions 仓库变量 `FN_MUSIC_UPDATE_MANIFEST_URL` 已配置为 `https://<R2_PUBLIC_DOMAIN>/update.json`；首个发布基线仍需由管理员在受 Access 保护的后台明确选择 Release 并二次确认。
- GitHub Fine-grained PAT `fn-music-tv-update-publisher` 已作为 Worker Secret `GITHUB_TOKEN` 配置，有效期至 2027-08-11；到期前需要轮换，否则只影响发布后台读取 GitHub，不影响已发布的 R2 更新。
- Cloudflare 普通 R2 自定义域名并不等同于 Cloudflare 中国网络，国内访问速度与稳定性需要在真实网络中验证；本版本明确不增加备用源。
- Android TV 厂商对“安装未知应用”设置页和系统安装界面的呈现可能不同，必须在目标设备或代表性模拟器上验证授权返回和取消路径。
- 本任务已经从单纯 UI 扩展为 App、CI 与 Cloudflare Worker 发布后台的复合功能；`design.md` 与 `implement.md` 必须在进入实现前根据本 PRD 重新收敛。
